## 1. 研究背景

### 社会課題
- 災害時は道路が途切れて、被災の状況がなかなか分からない。そこでドローンで上から撮影して、状況を確かめる。
- 広い範囲を早く見るため、**複数のドローン**を同時に飛ばす。
- しかし災害時は基地局が壊れたり弱ったりして、回線が細くなる（論文9 Liu ら）。複数のドローンが、1つの基地局（または中継局）の細い回線を取り合う。
- 回線が詰まると、被災が写った画像も、何も写っていない平常の画像も、同じように待たされる。**本部に被災の情報が届くのが遅れる。**

### 今の基地局の混雑対策
- 携帯電話の基地局は、混んだときに「誰に電波を割り当てるか」をスケジューラで決めている。優先度は「通信の種類」（通話・動画など、5G の 5QI）や「誰の通信か」（災害時優先電話など）で決まる。
- **画像に何が写っているか（中身）では、優先度を決めていない。**

### 先行研究で分かっていること
- 「エッジの軽いAIでふるいにかけ、迷った画像だけサーバーに送る」仕組みは、2017年ごろに確立している（論文1 NoScope、論文2 DDNN、論文7 Neurosurgeon）。
- 送らない画像を作る方が、モデルを途中で切って全部送る方式より速い（論文8 DCSB：8Mbps で推論時間 92〜95% 減）。
- 災害の空撮画像は、ドローンに載る軽いモデルで分類できる（論文6 EmergencyNet：AIDER で F1 95.7%、ARM Cortex-A57 で約25枚/秒）。
- 中身を見て、複数のカメラの間で優先して送る研究はある（Vigil：均等配分より関係する物体を最大25%多く届けた）。災害時に優先度を付けて送る研究もある（Desher ら：救助隊などの利用者を優先）。
- しかし、**エッジAIが画像から出した「被災っぽさ」を、複数ドローンが共有する基地局での送る順番に使い、実際の災害画像で「被災画像が本部に届くまでの時間」を評価した研究は、調べた範囲では見つからなかった**（2026-10-15、3方向で検索。詳しくは 7章）。

### 実現性テストで分かったこと（2026-10-14、`experiments/feasibility/`）
- AIDER は公開されていてすぐ使える。学習済みのモデルを使えば CPU だけで動く。
- エッジ役のモデルは被災画像 614 枚のうち 33 枚を「平常」と見逃し、そのうち 10 枚は確信度 0.8 以上だった。
- 判定（送るかどうか）を変えても、見逃し率は変わらなかった（どの方式も 3.3%）。
- 回線が詰まったときは、送る順番を「被災っぽい順」にすると、被災画像が確認されるまでの平均が 12.5秒 → 6.3秒 に縮んだ。
- → **効果が出るのは「判定」ではなく「順番」**。なので、判定は既存のまま、順番を決める部分を研究する。

## 2. 研究目的

複数のドローンが細い回線を共有する災害時に、**同じ回線のままで、被災の情報をより早く本部に届ける**。

具体的には、次の問いに答える。
1. 基地局で「被災っぽい順」に通すと、到着順や公平な順番と比べて、被災画像が本部に届くまでの時間はどれだけ縮むか。
2. その効果は、ドローンの台数・被災画像の割合・回線の速さによって、どう変わるか（どんな条件なら効くか）。
3. 優先した分、平常の画像はどれだけ遅れるか（代わりに失うもの）。

「回線そのものを速くする」研究ではない。送れる量は同じで、順番を変えることで大事な情報を先に届ける。

## 3. 提案手法

### 全体の流れ
```
ドローン1 ─┐
ドローン2 ─┼─▶ 基地局（細い回線を共有） ─▶ 本部のサーバー
ドローンN ─┘     ↑ ここで通す順番を決める（提案）
```

1. **ドローン（エッジ）**：撮った画像を軽いモデルで分類する。
   - 送るかどうかは**既存の方式のまま**にする（「確信度が低いものだけ送る」、論文1・2の基本形）。どの方式でも、送る画像はまったく同じにする。
   - 送る画像には、モデルが出した「**被災っぽさの点数**」 s = 1 − P(平常) を付ける（数バイト）。
2. **基地局（提案）**：回線が混んでいるとき、待っている画像の中から、次に通す画像を決める。
   - 提案1：点数 s が高い順に通す
   - 提案2：点数に「待ち時間」を足す（優先度 = s + α × 待ち時間）。平常の画像がいつまでも届かない問題を防ぐ
3. **本部のサーバー**：届いた画像を、重い（精度の高い）モデルで分類し直す。

### 比べる方式（送る画像はどれも同じで、基地局の順番だけ違う）
| 方式 | 基地局の順番 | 何のつもりか |
| --- | --- | --- |
| 到着順 | 来た順に通す | 今の基地局に近い |
| ドローンごとに順番 | ドローンを順番に回す | 公平さを重視する今の考え方（Vigil の比べる相手の「均等配分」に近い） |
| 提案1 | 被災っぽい順 | |
| 提案2 | 被災っぽさ＋待ち時間 | |
| （参考）全部送る | 到着順 | ふるいにかけない場合 |
| （参考）エッジだけ | 送らない | 回線を使わない場合 |

## 4. 研究方法

### 4.1 データ
- **AIDER**（論文6 の著者が作った災害空撮データセット）。Zenodo で公開、CC BY 4.0。取り方は README の `scripts/fetch_external.ps1`。
- 公開版は 6,433 枚（平常 4,390、洪水 526、火災 521、倒壊 511、事故 485）。学習 50% / 検証 20% / テスト 30% に分ける（乱数の種を固定）。
- **被災画像の割合を変える**：AIDER は被災が約3割で、実際の飛行よりかなり多い。テスト用の流れから被災画像を間引いて、5% / 10% / 30%（そのまま）の3通りを作る。

### 4.2 モデル
- エッジ：EmergencyNet（`external/EmergencyNet` の学習済みの重み）。動かせなければ、実現性テストと同じ MobileNetV3-Small を使う。
- サーバー：ImageNet で学習済みの重いモデル（実現性テストでは ConvNeXt-Tiny）を AIDER で学習させる。
- モデルの精度は研究の主題ではない。両方の方式で同じモデルを使う。

### 4.3 シミュレーションの条件（**実験の前に決めておき、結果を見てから変えない**）
| 条件 | 値 | 根拠 |
| --- | --- | --- |
| ドローンの台数 | 1 / 3 / 5 / 10 台 | 回線の詰まり方を変えるため |
| 1台が撮って分類する枚数 | 2枚/秒 | 論文1 NoScope が 30fps の動画を15フレームおきに間引く例（＝2枚/秒）。隣の画像は重なるので全部は要らない |
| 送る画像の大きさ | 240×240 の JPEG（品質85、平均約14KB） | EmergencyNet の入力の大きさ（論文6） |
| 送るかどうか | 確信度が低いものを送る。送る割合は全体の約40%（検証用データでしきい値を決める） | 論文1・2 の基本形。実現性テストと同じ |
| 回線 | 1Mbps 固定 / 200kbps 固定 / 10Mbps → 1Mbps → 200kbps と細くなる | 1Mbps：論文7 の実測で、3G は 152KB を送るのに 870ms 以上（約1.4Mbps 以下）。200kbps：さらに弱った場合の仮定。比較のため、論文4 の 4G の上り（8〜48Mbps）も参考に書く |
| 飛行時間 | 一定の時間で撮影を終える（例：10分） | 「飛行中に届いた被災画像の割合」を測るため |
| くり返し | 流す順番を変えて 10 回、平均と幅を出す | |
| 提案2 の α | 検証用の流れで1つ決めて固定 | |

### 4.4 測る数字（指標）
| 指標 | 意味 | 一番大事か |
| --- | --- | --- |
| 被災画像の 90% が本部で確認されるまでの時間 | 被災の状況がほぼそろうまでの時間 | ◎ |
| 最後の被災画像が確認されるまでの時間 | 一番遅れた被災情報 | ○ |
| 飛行中に届いた被災画像の割合 | 回線が詰まりすぎたとき用 | ○ |
| 被災画像の遅延（平均・95%値） | 論文4 Zhao らも中央値と99%値で測っている | |
| 平常の画像の遅延 | 優先した分の代わりに失うもの | |
| 送ったデータ量（バイト） | 論文2 DDNN と同じく、バイトで数える。どの方式も同じになることを確かめる | |
| 被災の見逃し率 | 判定は同じなので、どの方式も同じになるはず（確認用） | |

### 4.5 先行研究の数値の使い方
| 論文 | 使う数値 | 何に使うか |
| --- | --- | --- |
| 6 EmergencyNet | F1 95.7%、約25枚/秒（ARM Cortex-A57）、パラメータ約9万 | エッジのモデルの基準。自分たちで AIDER 公開版の F1 を測って比べる（実現性テストの MobileNetV3 は 90.0%）。25枚/秒は「2枚/秒なら十分間に合う」根拠 |
| 1 NoScope | 30fps を15フレームおき（＝2枚/秒）に間引く例 | 撮って分類する枚数の根拠 |
| 7 Neurosurgeon | 152KB の画像を送るのに 3G で 870ms 以上、LTE で 180ms | 「送る時間が計算より長い」動機と、1Mbps 条件の根拠 |
| 4 Zhao ら | 4G の上り 8〜48Mbps、遅延の中央値 72ms、回線の変化への反応 3.4倍速 | 回線条件の参考と、遅延の測り方（中央値・99%値）。コードの `configs/link_profiles.yaml` |
| 8 DCSB | 帯域 74〜82% 節約、8Mbps で推論時間 92〜95% 減 | 「送らない画像を作る」方向の根拠 |
| 2 DDNN | 通信量をバイトで数える、しきい値ごとの表 | 指標の数え方と、結果の見せ方 |
| 3 Choi ら | （数値は要旨にない） | 「精度の条件を守って遅延を最小にする」問題の立て方の参考 |
| 5 ClassyNet | （優先クラスの推論が最大4倍速い） | クラスの優先度の先行例。違い（1台の中の計算か、回線での順番か）を書くため |
| 9 Liu ら | （数値は要旨にない） | 災害時に基地局が壊れ、帯域が足りないという背景 |
| Vigil（MobiCom 2015） | 均等配分より関係する物体を最大25%多く届けた | 一番近い先行研究。比べる方式「ドローンごとに順番」の考え方 |

先行研究の数値を、自分たちの結果と横に並べて比べることはしない（データも回線の条件も違うので意味がない）。比べるのは、**同じデータ・同じ回線の条件で再現した方式どうし**。

### 4.6 予想（実験の前に書いておく）
- 被災画像の割合が 30%（AIDER そのまま）のとき：送る画像の約8割が被災っぽい画像なので、順番を変えても、最後の被災画像までの時間は**最大で2割ほどしか縮まない**と予想する。
- 被災画像の割合が 5% のとき：送る画像のほとんどが平常の画像になるので、被災画像は大きく先に届き、**数倍以上の差**が出ると予想する。
- 回線が詰まらない条件（台数が少ない、回線が太い）では、どの方式も差が出ない。
- 予想どおりにならなくても、「どの条件で効くか・効かないか」をそのまま結果にする。

### 4.7 この研究でやらないこと
- 回線を実際に絞る実験（Linux の netem）、実機（Raspberry Pi・Jetson・ドローン）での計測。時間があれば netem だけ試す。
- 分類モデルの精度を上げること。
- 基地局の本物のスケジューラ（通信会社の設備）を変えること。現実には、5G の QoS の設定やローカル5G で実現できる、と考察で書く。

## 5. 新規性と、言えないこと

### 新規性（組み合わせ）
- エッジAIが画像から出した「被災っぽさ」を、複数ドローンが共有する基地局で通す順番の優先度に使う。
- 待ち時間も考えて、平常の画像が届かなくなるのを防ぐ。
- 実際の災害空撮画像（AIDER）で、「被災画像が本部に届くまでの時間」を、台数・被災の割合・回線の速さを変えて評価する。

### 言えないこと（すでにある）
- 「中身で優先度を決めて送る」こと自体（Vigil、PRoFFAN など）
- 「AIの判定結果で、基地局が端末の送る順番を決める」こと自体（Liu ら TCCN 2020、Pillai ら 2026）
- 「重要度 × 待ち時間で順番を決める」こと自体（UoI、AoSI、SAoI）
- 優先度付きの待ち行列そのもの（通信では昔からある）

## 6. 今後の予定（残り：今日の1時間 ＋ 6週間）

ゼミは1回150分。3人で分担し、ゼミの時間以外の作業は宿題にする。担当（A・B・C）は3人で決める。

### 今日（残り1時間）
- [ ] テーマをこの案にするか、3人で決める（決まらなければ、決まらなかった理由と次の候補を書く）
- [ ] 決まったら、担当 A・B・C を決める
- [ ] 各自 `.\scripts\fetch_external.ps1` を実行し、データとコードを手元にそろえる

### 担当（案）
- **A：基地局のシミュレーション**（複数ドローン、回線、待ち行列、順番の決め方）
- **B：モデル**（エッジは EmergencyNet、サーバーの学習、被災っぽさの点数を出す）
- **C：実験の管理と集計**（条件の表、くり返しの実行、指標の計算、グラフ）

### 6週間の予定
| 週 | やること | その週の完成の条件 |
| --- | --- | --- |
| 1 | 研究計画書を3人で直して決める。条件（4.3）と指標（4.4）を確定する | 計画書が main にマージされる |
| 2 | B：EmergencyNet を AIDER 公開版で動かして F1 を測る（論文6 の 95.7% と比べる）。A：実現性テストのプログラムを、複数ドローン・基地局の形に作り直す | エッジの F1 が出る。1台の場合で、実現性テストと同じ結果が再現できる |
| 3 | A：比べる方式（到着順・ドローンごと・提案1・提案2）を全部入れる。C：被災の割合を変えたテスト用の流れを作る | 全部の方式が1つの条件で動く |
| 4 | C：本番の実験。台数 × 被災の割合 × 回線 の全部の条件を、10回ずつ回す | 全条件の結果の表ができる |
| 5 | 結果をグラフにして考察する。予想（4.6）と合ったか、どの条件で効いたかを整理する。時間があれば netem で1条件だけ実測 | グラフと考察の下書き |
| 6 | 発表資料・デモ・論文（5ページ程度）を仕上げる | 成果物がそろう |

### 途中で判断すること
- **2週目の終わり**：EmergencyNet が動かなければ、MobileNetV3-Small に切り替える（実現性テストで動作確認済み）。
- **4週目の途中**：どの条件でも差が出なければ、「優先度が効かない理由」（被災の割合、回線の余裕など）を調べる方向に切り替える。それも結果として発表する。
