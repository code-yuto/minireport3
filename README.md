### 議事録のルール
- 提出用の議事録は、これまでどおり **Word で作る**（提出はWordが必須）
- GitHub では Word は管理せず、**md に変換して `giziroku/` に置く**。md への変換は **渡部** がやる
- ファイル名は `weekNN_YYYY-MM-DD.md`（例：`week01_2026-10-01.md`）。追加したらこの表にリンクを足す
- 「来週の達成目標」は次週の宿題としてチェックリスト（`- [ ]`）で書く
- 議事録の PR は、tsukahara と yamashige が読んだら Approve する。**全員が内容を確認した印**にする

## 運用ルール

### 大原則
- **1つの作業 = 1つの issue = 1つのブランチ = 1つの PR**
- **main に直接 push しない。** 自分のブランチで書いて、PR を通して main に入れる
- **決めたことは issue や PR に書いて残す**（口で決めたことも書く）

### issue
- やることを1つ書く。本文には「何のために」と「完成の条件（チェックリスト）」
- Assignees に担当者を入れる

### ブランチ
- 名前は `種類/issue番号-内容`（例：`docs/1-survey-watanabe`）
  - `docs/` 文章・まとめ、`feature/` 新しい機能やコード、`fix/` 間違いの修正

### commit
- 意味のある区切りで、小さく何回も（例：1項目書くごとに1回）
- メッセージは `docs: 論文の要約を書く` のように、種類 + 何をしたか
- 自分の担当以外のファイルは混ぜない

### PR
- 本文に「何をしたか / なぜしたか / どうやって確認したか」と `Closes #issue番号` を書く
- 途中で見てほしいときは Draft のまま、書き終わったら **Ready for review** にする
- Reviewers に、書いた人以外の2人を入れる

### レビュー
読んだ結果によって、次の3つを使い分ける。

| 読んだ結果 | 選ぶもの |
| --- | --- |
| 直すところがない | **Approve** |
| 質問や、できればという提案だけ | **Comment** |
| 直さないとマージしないほうがいい | **Request changes** |

- 具体的な指摘は、Files changed で行の横の **＋** から行ごとにコメントする
- 指摘するのは人ではなく内容。「〜はどうですか？」と提案の形で書く
- 指摘を直したら同じブランチで commit・push し、そのコメントを **Resolve conversation** で閉じる

### マージの条件
**書いた人以外の2人がそれぞれ OK を出したらマージする。**

PR は全部 code-yuto のアカウントで作ったため、GitHub の仕様で watanabe はどの PR も Approve できない。そこで、watanabe の OK は Comment で「OK」と書くことで代わりにする。

| PR | OK を出す人 |
| --- | --- |
| #2（watanabe） | tsukahara（Approve）・yamashige（Approve） |
| #4（tsukahara） | yamashige（Approve）・watanabe（Comment で「OK」） |
| #6（yamashige） | tsukahara（Approve）・watanabe（Comment で「OK」） |

- OK がそろったら、**書いた人**が **Squash and merge** を押す
- マージしたらブランチを削除する

### 手元に最新版を残す
- 書き始める前・ブラウザで編集したあと・マージのあとに、必ず `git pull`
- 最新版になっているかの確認

```sh
git fetch
git status            # 「Your branch is up to date」ならOK
git log --oneline -3  # 一番上の英数字7桁が GitHub のコミット一覧と同じならOK
```

### 入れてはいけないもの
- 論文の PDF そのもの（著作権）。タイトル・URL・DOI を書く
- データセットの本体や大きいファイル。入手先の URL を書く
- パスワードや API キー（`.env`）

## この運用のメリット
- **main がいつもきれい**：確認済みの内容しか main に入らないので、main を見れば「チームで合意した最新版」がわかる
- **誰が何をしているか一目でわかる**：issue と Assignees を見れば、担当と進み具合がわかる。リーダーに任せきりにならない
- **お互いに読み合うので、理解がそろう**：レビューで他の人のまとめを読むことになり、3人とも全分野の内容を知った状態で次のステップ（社会的な問題・技術・データセット決め）に進める
- **ミスに早く気づける**：数字の間違いやわかりにくい説明を、マージ前に別の人が見つけられる
- **履歴が残る**：いつ・誰が・なぜ変えたかが commit と PR に残る。論文を書くときに経緯をたどれる
- **ぶつかりにくい**：1人1ファイル・1人1ブランチなので、同じ場所を同時に書き換えることがほとんどない
- **間違えても戻せる**：commit ごとに状態が残っているので、前の版にいつでも戻せる
- **ゼミの目的に合っている**：資料の「助け合う / 進行役を交代 / 誰も孤立させない」を、レビューの仕組みで自然に実現できる
